## 3. What Was Implemented

### M3.1 — Repository Detection

**Question answered:** Is this target inside a Git repository?

Implementation invokes `git rev-parse --show-toplevel` against the analysis target. A non-zero exit code (Git's exit 128 — not a repository) is treated as a clean negative, not an application error. The result is `GitInfo.IsRepository = false` and Pulse continues normally.

Key decision: detection runs against `resolvedTarget.Path`, not `rootResult.Root`. This preserves the Pre-S3 boundary invariant — the user's explicit analysis target is never silently replaced.

---

### M3.2 — Repository Metadata

**Question answered:** Which repository is this?

Once a repository is confirmed, the repository root path returned by Git is cleaned with `filepath.Clean` for cross-platform consistency. The repository name is derived deterministically from `filepath.Base(root)` — no remote calls, no network dependency, no assumptions about hosting provider.

The `RepositoryRoot` and the analysis target are kept as separate values throughout. A test explicitly asserts they differ when the analysis target is a subdirectory.

---

### M3.3 — Branch / HEAD State

**Question answered:** Where is HEAD?

Implementation invokes `git symbolic-ref --short HEAD`. When the repository is in detached HEAD state, Git exits non-zero and `symbolic-ref` produces no output. Rather than treating this as a failure, `currentBranch` returns the explicit sentinel value `"HEAD"`. No crash, no invented branch name, no silent fallback.

---

### M3.4 — Working-Tree State

**Question answered:** Is the working tree clean or dirty?

Implementation invokes `git status --porcelain`. An empty response means clean. Any output means dirty. The result is typed as `WorkingTreeState` — a named string type with three defined constants:

```go
WorkingTreeClean   = "clean"
WorkingTreeDirty   = "dirty"
WorkingTreeUnknown = "unknown"
```

`WorkingTreeUnknown` is reserved for genuine Git command failures, keeping the type honest about what it represents.

## 4. Architecture

### New Type: `GitInfo`

```go
type GitInfo struct {
    IsRepository     bool
    RepositoryRoot   string
    RepositoryName   string
    Branch           string
    WorkingTreeState WorkingTreeState
}
```

Structured domain value. No strings assembled by the CLI. No formatting logic inside `internal/git`.

---

### Package Responsibilities

```
internal/git
    git.Discover(targetPath string) (GitInfo, error)
        repositoryRoot(targetPath)     -- M3.1
        repositoryName(root)           -- M3.2
        currentBranch(root)            -- M3.3
        workingTreeState(root)         -- M3.4
        run(dir, args...)              -- centralized exec
```

All `exec.Command("git", ...)` calls are contained inside `internal/git`. No Git invocations exist in `cli`, `snapshot`, or `output`.

---

### Pipeline Integration

```
Config
  ↓
Target (resolvedTarget.Path)
  ↓
Project Discovery
  ↓
git.Discover(resolvedTarget.Path)
  ↓
GitInfo
  ↓
ProjectSnapshot.Git
  ↓
Output (terminal + JSON)
```

`Discover` in `internal/snapshot` was extended with a single additional step. The existing pipeline was not restructured.

---

### Error Handling

| Situation | Behaviour |
|---|---|
| Target not a Git repository | `IsRepository = false`, no error returned |
| Git detected, command fails | `pulseErrors.Environment(message, cause)` returned |
| Detached HEAD | `Branch = "HEAD"`, no error |
| Git not installed | `repositoryRoot` returns `false, nil` — treated as non-repository |

No panics. No direct writes to stdout/stderr from `internal/git`. All errors flow through the existing `internal/errors` system.

## 11. Foundation for Next Milestones

`GitInfo` is intentionally flat and extensible. The second half of S3 — commit analytics, health signals, contributor data — can be added as new fields on `GitInfo` or as a separate enrichment step in the pipeline without restructuring anything that was built here.

The boundary between `RepositoryRoot` and the analysis target is already tracked separately and tested, which will matter when commit-range queries need to know which part of a monorepo is under analysis.
