## 3. Milestone Delivery

### M2.5 — Language Detection

**Commit:** `5329ead` — `feat(project): detect project languages`

**Problem solved:**
Project type detection answers what ecosystem a project belongs to. Language detection answers what languages are physically present in the source files. These are deliberately separate concerns. A Node.js project may contain TypeScript, CSS, HTML, and Markdown. A Go project may contain PowerShell build scripts and Markdown documentation.

**Implementation:**

Added `internal/project/language.go` containing:

- A `Language` type backed by `string` for named, type-safe language constants
- 14 named language constants covering the initial mapping specified in the brief
- A single `extensionMap` — the authoritative source for extension-to-language resolution. Adding a new language requires one line here and nowhere else
- `DetectLanguages([]string) []Language` — accepts a slice of file paths, extracts extensions, maps them, deduplicates via a set, and returns alphabetically sorted results

**Design decisions:**

| Decision | Rationale |
|---|---|
| Input is `[]string` file paths, not `scanner.Inventory` directly | Keeps the function pure and testable without filesystem coupling |
| Unknown extensions are silently ignored | Unknown is normal. It must never cause an error |
| Deduplication via `map[Language]struct{}` | O(1) membership, no duplicates by construction |
| Alphabetical sort as ordering strategy | Deterministic across all executions regardless of filesystem or map iteration order |
| Single `extensionMap` as authority | One place to extend. No scattered switch statements |

**Also delivered in M2.5:**

Added `AssertEqual[T comparable]` generic helper to `internal/testhelpers`. The language tests were written against this helper but it did not exist in the package. Rather than changing the tests to work around the gap, the helper was added where it belongs — in testhelpers — so all future tests can use it.

**Tests:** 9 tests covering single language, multiple languages, deduplication, unknown extensions, mixed known and unknown, deterministic ordering, nested file paths, empty input, and C vs C++ as distinct languages.

### M2.6 — Project Metadata

**Commit:** `4c83f53` — `feat(project): add project metadata`

**Problem solved:**
The discovery pipeline was producing several pieces of information — root path, project type, filesystem inventory — but they lived in separate variables with no coherent owner. M2.6 created a `Metadata` struct that combines all of it into a single named value, with all calculations performed at construction time.

**Implementation:**

Added `internal/project/metadata.go` containing:

- `Metadata` struct with fields: `Name`, `Root`, `Type`, `Languages`, `FileCount`, `DirectoryCount`
- `NewMetadata(root string, detection Detection, inv scanner.Inventory) Metadata` — the single construction point

**Design decisions:**

| Decision | Rationale |
|---|---|
| Project name derived from `filepath.Base(root)` | Safe, always available, requires no file parsing. Manifest-based naming is a future capability |
| `FileCount` and `DirectoryCount` sourced from scanner inventory | Consistent with scanning rules. Excluded directories do not contribute |
| Root directory excluded from `DirectoryCount` | Convention documented explicitly. `internal/` counts as 1; the project root itself does not |
| Language detection called inside `NewMetadata` | No second filesystem walk. The inventory file list is reused |
| All calculations in the project package, not in output | Output renders values that already exist. It does not compute them |

**Tests:** 7 tests covering name presence, root preservation, type propagation, file count, directory count, language detection integration, and empty project safety.

### M2.7 — Project Snapshot

**Commit:** `bfaba23` — `feat(snapshot): introduce project snapshot`

**Problem solved:**
Before M2.7, the CLI orchestrated every discovery step manually and passed individual results between functions. Future Pulse engines — Git analysis, health checks, documentation scanning — would each need to repeat that orchestration or receive a growing list of parameters. M2.7 introduced a single canonical representation of discovered project state and a single function that constructs it.

**Implementation:**

Replaced the placeholder `internal/snapshot/snapshot.go` with:

- `ProjectSnapshot` struct — the complete domain model of a discovered project
- `Discover(targetPath string) (ProjectSnapshot, error)` — the single orchestration function that runs the full pipeline: target resolution → root discovery → filesystem scan → type detection → metadata → snapshot

**`ProjectSnapshot` fields:**

```go
type ProjectSnapshot struct {
    Name           string
    Root           string
    Type           project.ProjectType
    Languages      []project.Language
    Files          []scanner.FileEntry
    Directories    []scanner.DirEntry
    FileCount      int
    DirectoryCount int
}
```

**Design decisions:**

| Decision | Rationale |
|---|---|
| Snapshot owns the raw `Files` and `Directories` slices | Future engines may need to inspect individual files, not just counts |
| Both count fields and slice fields are present | Counts are convenience accessors. They always equal `len(Files)` and `len(Directories)` |
| No filesystem handles or runtime state in the struct | The snapshot is safe to pass anywhere, hold indefinitely, and serialize |
| `Discover` is the only public construction path | Callers do not need to know the pipeline steps. They ask for a snapshot and receive one |
| No output-specific formatting in the struct | This is a domain model. Formatting is the output package's concern |

**Why this matters architecturally:**

```
                     ProjectSnapshot
                           │
          ┌────────────────┼─────────────────┐
          ▼                ▼                 ▼
      Git engine      Health engine     Docs engine
          │                │                 │
          ▼                ▼                 ▼
         S3               S4+             future
```

Every future Pulse capability receives a snapshot. None of them re-run discovery.

**Tests:** 5 integration-level tests covering a Go project fixture, an empty project, a mixed-language Node project, an invalid target, and deterministic output across two consecutive calls.

### M2.8 — Discovery Output

**Commit:** `a6a157d` — `feat(output): expose project discovery results`

**Problem solved:**
Pulse had internal intelligence but no way to show it. M2.8 wired the snapshot to both output formats and updated the CLI to use the unified discovery pipeline.

**Implementation:**

**`internal/output/output.go`** — two new methods added, existing methods preserved:

- `PrintDiscovery(snap ProjectSnapshot)` — terminal output
- `PrintDiscoveryJSON(snap ProjectSnapshot) error` — JSON output
- `JSONDiscoveryResult` and `JSONProjectSection` — exported types for the JSON schema, testable by value

**`internal/cli/cli.go`** — simplified and updated:

- When no target path: existing `PrintSummary` / `PrintJSON` placeholder paths preserved. All existing CLI tests continue to pass without modification
- When target path provided: calls `snapshot.Discover`, then routes to `PrintDiscovery` or `PrintDiscoveryJSON`
- Removed the manual pipeline orchestration that previously lived in `cli.go`. The CLI no longer needs to know about scanners, detectors, or root discovery. It calls `Discover` and renders the result

**Terminal output format:**

```
Pulse v1.0.0

  Name: pulse
  Type: Go
  Root: C:\Users\ragha\Documents\Anti-grav\pulse

Languages
  Go
  Markdown
  PowerShell
```

**JSON output format:**

```json

  "version": "1.0.0",
  "project": {
    "name": "pulse",
    "root": "C:\\Users\\ragha\\Documents\\Anti-grav\\pulse",

      "Go",
      "Markdown",
```

**JSON API properties:**

- No ANSI sequences or human decorations
- Stable field names with snake_case convention
- Deterministic language array — alphabetically sorted
- Valid JSON on every success path
- Errors remain on stderr, never in the JSON body
- `JSONDiscoveryResult` and `JSONProjectSection` are exported — tests unmarshal directly into the typed structs rather than parsing raw maps

**Tests added:** 10 new output tests covering name, type, root, languages, counts, no-language case, stdout isolation, JSON validity, JSON field values, and JSON stderr isolation. All 6 pre-existing output tests preserved and passing.

## 4. Technical Issues Encountered

Two issues arose during implementation, both caused by PowerShell here-string encoding behaviour rather than logic errors.

### Issue 1 — Wrong module path in language test file

`language_test.go` was pre-written with import path `github.com/jabuta/pulse/internal/project`. The module is named `pulse` in `go.mod`, not `github.com/jabuta/pulse`. The file would not compile.

**Resolution:** The import path was corrected to `pulse/internal/project`. This was a one-line fix once the module name was confirmed from `go.mod`.

### Issue 2 — PowerShell here-string corruption of special characters

When writing Go source files via PowerShell `@'...'@` here-strings, two classes of corruption occurred repeatedly:

1. **Backtick struct tags** — Go struct tags use backtick delimiters (`` ` ``). PowerShell here-strings treat backticks as escape characters and consumed them, producing invalid syntax such as `Version string json:"version"` instead of `` Version string `json:"version"` ``

2. **Em-dash characters in comments** — Unicode em-dashes in doc comments were corrupted to invalid UTF-8 sequences, causing `illegal UTF-8 encoding` compiler errors

3. **Trailing backslash** — A stray `\` was appended to the end of one file

**Resolution:** Two mitigations were applied:

- Struct tags written using `[char]96` interpolation to produce literal backtick characters: `[char]96 + 'json:"version"' + [char]96`
- Files written via `[System.IO.File]::WriteAllText` with an explicit `UTF8Encoding` constructor rather than `Set-Content`, which avoids BOM and encoding ambiguity
- Em-dash characters replaced with plain ASCII alternatives in doc comments

These are tooling constraints, not architectural issues. All files are correctly formatted and compile cleanly.

## 8. What Pulse Is Now

At `0.1.0`, Pulse was a CLI shell: argument parsing, version output, error handling, stdout/stderr separation.

At `0.2.0`, Pulse is a project intelligence tool. It can be pointed at any directory and will return:

- The project name
- The project root
- The detected ecosystem type
- Every programming and markup language present in the source files
- The file and directory counts

It returns this in a human-readable terminal format and in a stable, machine-readable JSON format suitable for scripting and IDE integration.

More importantly, it now has a `ProjectSnapshot` — a deterministic, serializable domain model of a project — that becomes the input to every future Pulse capability. S3 (Git intelligence), S4 (health analysis), and everything beyond it will consume a snapshot. They will not re-run discovery.
